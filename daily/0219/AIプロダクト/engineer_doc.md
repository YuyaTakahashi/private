# WMS/SCMプロダクトへのAI実装 PoC 概要（開発部資料まとめ）

## 1. 目的とプロジェクトステータス
- **目的**: 将来的な「自律型AIエージェント」の実装に向けた第一フェーズ（技術検証PoC）。複雑化したUXを、自然言語によるデータ分析や業務実行で解消することを目指す。
- **直近の目標**: 2/26(木)の経営会議での状況共有とデモ実施。
- **現在のフェーズ**: 技術検証（PoC）。「開発が順調だったので、実用性・経営インパクトまで踏み込んで検証した」というストーリーで進める予定。

## 2. 実装イメージとユースケース
### アプローチ
- 「定型業務は従来のUI」＋「非定型・分析業務はAI」というハイブリッドUX。
- チャットボット形式だけでなく、「AIが背後でデータを繋ぎ、アクションを提案する」形を志向。

### 想定ユースケース
- **検索・特定**: 配送状況の確認、怪しい購入者（転売等）の特定。
- **分析・監視**: 不良発生率の監視、類似商品の販売実績比較、不動在庫のコスト計算。
- **検知・予測**: 売れ行きの急伸（スパイク）検知、出荷遅延リスクのある注文の特定。
- **アクション代行**: 「〇〇の出荷を止めて」といった指示に対し、JSONを生成してAPI経由で設定変更を実行。

## 3. 技術的構成
- **基盤**: LLM（Gemini-1.5-Pro等）を活用。
- **仕組み**: 
  1. ユーザーの文章をLLMが解釈
  2. LLMが必要なアクション（設定変更・データ取得）を判断
  3. API用のJSONを生成し、`openlogi-api`等で処理を実行
- **データソース**: 現状は `openlogi-api` が中心だが、将来的には `fraise-order-sync` や外部（Kintone, Hubspot）のデータ活用も視野。

## 4. 検討課題
- **正確性の担保**: AIの回答が正しいか、ユニットテストやQA視点での検証が必要。
- **UXの落とし穴**: チャット形式が本当に利便性を高めるか？「AIに聞く」という手間がハードルにならないか。
- **工数感**: 基盤構築からQA環境への反映まで、相当のエンジニア工数を投下している（具体的な工数算出中）。
- **運用の継続性**: 問い合わせ対応の代替（AIチャットボット）としての改善効果の継続。
