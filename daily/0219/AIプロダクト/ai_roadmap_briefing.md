# 【事前インプット】AIプロダクトの現在地と今後の向き合い方

## 本資料の目的
来月の経営合宿にて、開発部よりAIプロダクトの提案（PoCデモ等）が予定されています。
本資料は、それに先立ち「AIプロダクト開発」が従来の開発とどう違うのか、PdMとしてどのような視点でハンドリングしていくべきか、その共通認識を持つための情報提供を目的としています。

---

## 1. AIプロダクト開発における「常識」のアップデート

従来のプロダクト開発（確定的）とAI開発（確率論的）には、決定的な違いがあります。

| 項目                 | 従来のシステム開発       | AIプロダクト開発                                         |
| :------------------- | :----------------------- | :------------------------------------------------------- |
| **品質保証**         | 100%バグがないことが前提 | **「80~90%の正答率」をどう許容するか** の設計が必須      |
| **コスト構造**       | 開発費（初期）がメイン   | **推論（API実行）コスト**が定常的に発生                  |
| **開発リードタイム** | デモができれば完成に近い | **デモはすぐできるが、実用レベルへの調整に時間がかかる** |
| **必要な人材**       | ソフトウェエンジニア     | **AIエンジニア、データサイエンティスト**が必要           |

### ポイント
- 「それっぽいデモ」は今の技術なら数日で作れますが、**「本番で誤回答せずに動き続ける」ための作り込みには、従来の数倍のコストと不確実性**が伴います。

---

## 2. オープンロジが狙うべきAIの勝ち筋： 「AI BPO」という考え方

開発部からは「チャットボット」形式の提案が入る予定ですが、PdMとしてはその先の「ビジネスインパクト」に注目しています。

### 「予測（推論）」よりも「代行（自動化）」
- **難しいこと（予測）**: 需要予測や在庫適正化の推論。精度が100%でないと顧客は判断を預けにくく、結局「自分で考えたい」というニーズが勝ります。
- **価値があること（代行）**: 「誰がやっても同じだが、手間がかかる作業」をAIに肩代わりさせる。
    - 例：複雑な配送ルールの設定代行、注文データのクレンジング、定型的な問い合わせの一次返信。

### 目指すべき方向
顧客に「考えさせる（入力を強いるチャット）」ではなく、**顧客の「時間を浮かせる（裏側で終わっている）」AI BPO（労働力としてのAI）**の実現を目指すべきと考えています。

---

## 3. 今後の進め方とスタンス

現在、開発部が進めている「チャットUIを通じた補助機能」の実装自体には賛成しています。
まずは**「ユーザビリティを補完する補助機能」**としてスモールスタートし、以下の観点に留意しながら、経営判断の土台を整理していきたいと考えています。

- **UIの引き算**: チャット（対話）という手間を増やさず、むしろ操作を減らす活用ができるか。
- **リカバリー設計**: AIが間違えた時に、ユーザーが簡単に修正できる設計になっているか。
- **データ基盤の強化**: 将来的に勝てるAIにするために、今のうちから何のデータを溜めるべきか。

## 4. 経営合宿での議論に向けて
開発部がデモを披露する際、以下の3点を念頭に置いて見ていただけると、その後のロードマップ策定がスムーズになります。

1.  これは、現場や荷主の**「入力の手間」**を増やしていないか？
2.  **正解率が80%**だったとき、業務は回るか？
3.  この機能を**1万人が使い続けても、利益が出るコスト構造**か？
