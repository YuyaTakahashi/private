# AIワークフローとバイブコーディングの勘所 〜UX用語作成ツール開発の裏側〜

## 【結論】AIは「作業者」ではなく「システムを共に創るパートナー」

AIを単なる「便利なチャットボット」として使っているうちは、その真価の半分も引き出せていません。今回のUX用語作成ツールの開発を通じて得られた最大の学びは、**AIを「システムそのものを構築し、進化させるパートナー」として捉え直すことで、開発のあり方が劇的に変わる**ということです。

本記事では、一歩先のAI活用「バイブコーディング」を実現するための3つの核となる考え方をシェアします。

---

## 序章：AI活用の進化ステップ

### ステップ1：チャットLLM（一問一答の「道具」）

**代表例**: ChatGPT, Gemini, Claude

最もシンプルなAI活用。画面越しに対話して回答をもらう形式です。

- **イメージ**: ほしい情報を教えてくれる「物知りな先生」
- **得意な領域**: リサーチや調査、アイデアの壁打ち
- **人間のコスト**: 毎回の指示・相談が必要

### ステップ2：AIワークフロー（工程をつなぐ「工場」）

**代表例**: Dify, n8n

複数のAI処理や外部APIを「線」でつなぎ、工程を自動化します。

- **イメージ**: 材料を入れると完成品が出てくる「自動化ライン」
- **得意な領域**: 決まった手順（生成→推敲→保存）の自動化
- **人間のコスト**: 初期設計後は最小限

### ステップ3：AIエージェント（自律的に動く「助手」）

**代表例**: Antigravity, Claude Code, Microsoft Copilot (Agents), Codex

目標を伝えると、AI自らが手順を考え、実行し、結果を確認します。

- **イメージ（単体）**: 「これを直しておいて」と伝えれば自分で考えて完結させる「優秀な助手」
- **得意な領域**: 自律的なコード生成・修正、システムデプロイ
- **人間のコスト**: 目標設定と検証のみ

### ステップ4：組織型AIエージェント（複数AIの協調）

複数の異なる専門知識を持つAIが協調し、タスク自体を分解して委譲します。

- **イメージ（組織型）**: 「このプロジェクトを進めて」と指示すると、AI自身が計画を立て、各専門家に役割を割り振る「プロジェクトマネージャー」
- **得意な領域**: 複数AIが協調する複雑業務の自動化（現在検証中）
- **人間のコスト**: 初期設定のみ。以降は完全自動化を目指す

---

本記事では、ステップ2（ワークフロー）とステップ3（エージェント）を組み合わせた「バイブコーディング」、および進化系のステップ4（組織型AIエージェント）について解説します。

## article-creation のプロダクトアーキテクチャ

### システム全体図

[**図解：UX用語作成ツールの2層アーキテクチャ**]

- 左側：ユーザー/プロンプト入力
- 中央：Dify（オーケストレーション層）- ステップを矢印でつなぐフロー図
- 右側：LLM + GAS（実行層）
- 上部：Antigravity（統合エージェント）- 全体を監視・修正

### 司令塔：Dify（Workflow Orchestration）

Dify がLLM（生成）とGAS（決定論的タスク）のプロセスと情報の橋渡しを制御します。ユーザー入力から出力まで、各ステップのフロー管理を一元化。

- **役割**: ステップの連結、条件分岐、外部API呼び出し
- **管理対象**: プロンプト、変数、フロー順序

### 統合エージェント：Antigravity（Development & Integration）

Antigravityがシステム全体を監視・修正・更新します。

- **監視**: Difyのルール正当性、LLMプロンプト効果測定、GAS実行結果検証
- **修正**: エラー発生時の自動修正、パフォーマンス改善
- **更新**: Difyのワークフロー設定、プロンプト、GASコードの改善

## 【課題】単発プロンプトと手動運用の限界

開発の初期、私はGeminiやGPTに対し「UX用語を調査して、決まったフォーマットで解説して」という指示を単発で出していました。しかし、すぐに行き詰まりました。

- **品質の壁**: 1回の生成で「わかりやすく、深く、正確な記事」を作るのは難しく、結局人間が大幅に書き直す手間が発生。
- **管理の複雑化**: 生成用と推敲用のプロンプトを2つ打つのも面倒だし、出力結果をGoogleドキュメントにコピペする作業自体がボトルネックになる。

「いいものを作ろうとすればするほど、手間が増える」というパラドックスを解消するために必要だったのが、先ほどのアーキテクチャによるプロセスの自動化と役割分担でした。

## バイブコーディングの3つのコアスキル

### 1. AIリバースエンジニアリング：プロンプトを「書く」から「推測させる」へ

プロンプトエンジニアリングは本来、高度に抽象的な作業です。人間が「どう言えばAIが動くか」をゼロから頭を捻って考えるのは非効率です。

ここで、vitaryのワークショップで「プロンプトをAIに書かせる」という発想が活きてきます。**「AIは結果（正解データ）からプロセス（プロンプト）を推測するのが得意である」**という特性を逆手に取るのです。

### 実践のステップ
1.  **正解データを見せる**: 自分が「これは最高だ」と思う過去の用語解説記事をAIに読み込ませる。
2.  **プロセスの抽出**: 「このレベルの記事をたくさん生成するための、最高に効果的なプロンプトを設計して」と依頼する。
3.  **具体と抽象のループ**: 2のプロンプトで作った記事を微修正（具体）したら、「今までの指摘を分析し、設定してあるプロンプトを改善して」とAIに依頼する。AIが修正理由を分析してプロンプトを強化（抽象）する流れを繰り返す。

人間は「具体」に集中し、AIに「抽象化（プロンプトへの言語化）」を任せる。この役割分担こそが、リバースエンジニアリングの真髄です。

## 2. ドラえもん的エンジニアリング：なんでもお願いしてみるマインドセット

「AIにこれは無理だろう」という先入観ほど、進化を妨げるものはありません。たとえ自分がエンジニアであっても（あるいは非エンジニアであっても）、実装方法を悩む前に、まずは「四次元ポケットの道具」を取り出す感覚でAIに投げてみることが重要です。

システム構築の舞台裏（DifyのYAMLワークフロー設計やGASのコード構築）ですら、私は**「どう分ければいい？」「どんなステップが必要？」とAIに設計段階から丸投げ**しました。

### 「Vibe」を伝えることに徹する
エンジニアリングの役割は「どう作るか」から、AIに対して「何を実現したいか（Vibe：意図や感覚）」を正確かつ熱量を持って伝えることへとシフトしています。設計の善し悪しすらAIに評価させ、修正案をもらう。この「ドラえもん的エンジニアリング」が、開発スピードを異次元に引き上げました。

---

## 3. ドラえもんのポケットとしてのAntigravity：AIエージェントによる開発の統合

一発でAIが理想のシステムを構築することはできません。エラーが起こるたびにエラーメッセージを投げ、戻ってきた修正コードをローカルファイルにコピペしていては日が暮れてしまいます。

そこで、これらすべてのリソースを **Antigravity（AIエージェント）という一つの「ドラえもんのポケット」** に集約しました。

### 統合エージェントがもたらす開発体験
今の私は、Antigravityというポケットに向かって**「ここをもう少し優しく解説するように変えて」と一言指示するだけ**です。
するとAntigravityは自律的に：
- Difyのプロンプトノードを修正し（YAMLの再生成）
- その修正に合わせてGASのロジックが矛盾しないか確認し
- 必要ならGASを修正して本番環境へデプロイ（`clasp push`）する
- テストスクリプトを書いて簡易テストし、エラーが出れば原因を分析してコードを修正する（この間、人間は何もしていない）

システムそのものをAIエージェントとともに育てていく。これが、私が提唱する「バイブコーディング」の到達点です。

## 4. 組織型AIエージェント：複数AIの自律的なオーケストレーション（現在検証中）

これまでのアプローチは、1つのAIエージェント（AntigravityやClaude Code）がシステム全体を管理してきました。しかし、複数の異なる専門知識を持つAIが協調し、タスク自体を考え、他のAIに仕事を委譲する**「組織型AIエージェント」**への進化を現在試しています。

### AIチームのロスター

[**図解：AIエージェント組織図**]

- 中央：秘書エージェント（タスク受付・管理）
- 周囲：CPO → 複数PdM → デザイナー、リサーチャーなど（矢印で委譲関係を示す）

秘書エージェントが入口となり、複数の専門エージェントに自律的に委譲します。

| エージェント | 役割 |
| :--- | :--- |
| **秘書（secretary-ai）** | 入口。タスク受付・管理・エージェント選択・委譲 |
| **CPO相当（scm-product-owner-ai）** | 全体戦略・ロードマップ・優先度判断 |
| **PdM複数名（oms-pdm-ai, ims-pdm-ai, portal-pdm-ai）** | 個別プロダクト領域の要件定義・PRD作成 |
| **デザイナー（designer-ai）** | UX・デザインレビュー・ユーザー体験分析 |
| **リサーチャー（researcher-ai）** | 調査・競合分析・情報収集 |

**実行の流れ：**

1. タスクが秘書AIに到着
2. 秘書が「このタスクは誰の専門領域か」を判断（ai-teamのロスターを参照）
3. 該当エージェントへブリーフ（コンテキスト）を渡して委譲
4. 主担当エージェントが複雑なタスクを検知すれば、自律的に別のエージェントへ問い合わせ（秘書は仲介しない）
5. エージェント間の知識シェアリングと統合が自動進行

### ナレッジバックヤード：共有スキルと専門知識

[**図解：知識層の階層構造**]

- 下層から上層へピラミッド状に：プロトコル層 → スキル層 → ドメイン知識 → チーム情報 → 生きた文脈 → タスク記録
- 各層にエージェントがアクセス（矢印で示す）

複数のエージェントが協調するために、共有可能なスキル・ナレッジベースを階層化して整理しています。

| 知識層 | 内容 | 用途 |
| :--- | :--- | :--- |
| **プロトコル層** | エージェント共通の行動基準・ルール（`_base-protocol.md`） | すべてのエージェントがタスク実行時に参照 |
| **スキル層** | 各エージェントの専門知識と判断基準（各エージェントの `SKILL.md`） | 秘書が委譲時に読ませ、エージェント自身の行動指針 |
| **ドメイン知識** | 顧客・市場・製品の事実的知識（`domain/`） | 業界知識、既存制約、参照規格など |
| **チーム情報** | 定例会議・人間関係・方針（`team/`） | どの会議に持ち込むか、ステークホルダー判断 |
| **生きた文脈** | 直近の決定事項・判断の前提・スコープ外決定（`context/`） | エージェント間で最新の判断根拠を共有 |
| **タスク記録** | 各タスクのブリーフと成果物（`data/briefs/`, `data/artifacts/`） | 実行履歴・判断根拠・次のアクション |

秘書はタスク委譲時に必要なスキル・知識を抽出してエージェントに渡し、エージェント自身がナレッジベースを参照・検索する責任を持ちます。

### 現段階での試み

この組織型アプローチはまだ検証フェーズです。個別のエージェント能力よりも、「AIが自分たちの役割を認識し、タスクを分解し、最適な専門家に投げられるか」という**組織設計と委譲ロジック**が成否の鍵になっています。

人間が初期設定（秘書の起動、ロスターの定義、プロトコル）をしたら、以降のタスク実行は完全に自動化される世界へ。これが次のフェーズの「バイブコーディング」と考えています。

## キーテイクアウト

AIを「自分の代わりに作業をしてくれる部下」として見るのをやめ、「一緒に未来のシステムを創り上げるパートナー」として向き合ってみてください。

1.  **プロセスをAIに推測させる**（リバースエンジニアリング）
2.  **まずAIに相談・丸投げしてみる**（ドラえもん的マインド）
3.  **エージェントというポケットに集約する**（統合開発環境）

この3つのステップを自分たちの業務に当てはめたとき、どんな「四次元ポケット」が生まれるか。ぜひ、皆さんと一緒に探求していければと思います。
